# FR-004 — Authentication/account API salvage plan

**Labels:** `MUS`, `auth`, `security`, `scope-control`

## User Story
As a user, I want login and account-related flows to either work safely or be clearly disabled, so that the app does not present broken financial actions.

## Proposed Solution
Audit existing auth/account features and choose one MUS path: safe demo auth, real auth with serverless persistence, or explicitly disabled flows with clear copy.

## Implementation Flow
1. Inventory auth forms and account pages.
2. Identify dependencies on JWT, MongoDB, and backend Express routes.
3. Decide whether auth is MUS-real or MUS-disabled.
4. Implement the selected path and remove misleading broken behavior.

## Technical Approach
- If real auth: use serverless route handlers, hashed passwords, secure cookies, and robust validation.
- If demo/disabled: do not collect sensitive financial credentials.

## Key Considerations
- Financial-looking apps require extra caution around credentials and user trust.
- Never ship fake account workflows that look real without clear demo labeling.

## Acceptance Criteria
- [ ] Login/account behavior is documented.
- [ ] Broken auth calls to unavailable backend are removed.
- [ ] Sensitive forms are either secure or clearly disabled/demo-only.
- [ ] Security assumptions are documented for future work.
